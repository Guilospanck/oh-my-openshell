# Gateway set-up wizard and multi-gateway support: design

Date: 2026-10-27. Branch: `self-contained-osh`. Builds on the self-contained `osh`
(`docs/superpowers/plans/2026-10-27-self-contained-osh.md`).

## Intent and why

A person who runs `osh` for the first time should be walked, screen by screen, through choosing
which kinds of gateway they want, be told plainly what each needs and what is missing, and have
`osh` install whatever is missing. Later, on the Gateways tab, they can add another gateway
the same way. Linux must be able to do everything macOS can, including several gateways side by
side and the VM type. It must be friendly and look good.

## Goals

- A guided, full-screen wizard in the TUI: **Machine → Gateways → Review → Install → Done**
  (mockups approved by the user: layout "B", list on the left, details on the right; see
  `.superpowers/brainstorm/1601-1793115800/content/flow-b-v3.html`, regenerated by
  `scratchpad/gen.py`, and reproduced in "Screens" below).
- Gateway types, decided by the machine: **VM**, **Docker**, **Podman** on both macOS and Linux.
  Each type is `Ready`, `NeedsInstall` (with an explicit list of what will be installed or
  enabled), or `Unavailable` (with a plain reason, shown greyed out).
- Several gateways at once, any mix of types, on both platforms.
- The first gateway the user ticks is the **main** one (the CLI's default, port 17670). Every
  gateway is **named after its type**: `openshell-vm`, `openshell-docker`, `openshell-podman`.
- First run runs the wizard automatically (no gateway set up by osh yet); `osh setup` runs it
  again; Gateways tab key `a` opens it in "add" mode listing only types not yet added; `x` removes
  a gateway osh created (typed confirmation, like reset).
- Missing prerequisites are installed by osh with the consent rules already in force (every
  command shown first, sudo prompts answered by the user, `--yes` required without a terminal).
- Non-interactive form for scripts: `osh setup --gateways docker,podman --yes`
  (the first listed is main). `--runtime X` stays as an alias for `--gateways X`.

## Non-goals and anti-goals

- No mouse-driven UI work; keyboard only, like the rest of osh.
- Do not rename, restart or otherwise disturb a gateway the user already has (see "Existing
  gateways"). A wizard that breaks a working setup is a failure even if the feature works.
- Do not silently install anything: no step runs without being shown first.
- Not a general gateway manager: no remote or edge gateways, no editing ports in the UI.
- Not trying to boot a real microVM in tests (the test machines have no `/dev/kvm`).

## Facts established by reading the code and the real OpenShell 0.1.5 (evidence)

- The Linux package ships `/usr/libexec/openshell/openshell-driver-vm`. The VM driver needs
  `/dev/kvm` ("KVM access is required to run microVMs on Linux") and `mke2fs`, `debugfs`,
  `e2fsck` from `e2fsprogs`. `openshell-gateway config preflight --path gateway.toml` accepts the
  vm config on Linux (it checks the e2fsprogs tools, not KVM). So KVM must be detected by osh.
- `openshell gateway` has `add`, `remove` (registration only, stops nothing), `select`, `list`,
  `info`. No rename: a rename is `add` the new name, `remove` the old.
- `openshell gateway add <url> --local --name N` requires the mTLS certificates to already exist
  in `~/.config/openshell/gateways/N/mtls` (osh copies them from the main gateway's directory,
  as the existing macOS Docker flow does).
- The packaged Linux unit (`/usr/lib/systemd/user/openshell-gateway.service`) reads
  `~/.config/openshell/gateway.toml` and `~/.config/openshell/gateway.env`, keeps TLS in
  `~/.local/state/openshell/tls` (generated by `openshell-gateway generate-certs --server-san
  host.openshell.internal` in `ExecStartPre`) and its database under `~/.local/state/openshell/gateway`.
- The OpenShell installer starts the packaged service and registers a gateway called `openshell`
  on `127.0.0.1:17670`, and waits for it to report connected, which needs a working runtime for
  the docker and podman drivers (already handled: runtime installs before OpenShell on Linux).
- A gateway config's `[openshell.gateway] name` is the server's gateway id. The macOS Docker
  gateway already runs as an extra: name, three ports (17671, 17681, 17691), own database dir,
  TLS dir shared with the main gateway, run by `osh gateway-service` under a launchd agent.
- The podman driver auto-detects its socket (including `podman machine` on macOS, via
  `CONTAINER_CONNECTION` / `OPENSHELL_PODMAN_SOCKET`) and its gRPC endpoint from the bind address.

## Model

- `GwKind { Vm, Docker, Podman }`, names `openshell-vm|docker|podman`.
- `GatewaySpec { name, kind, port, main }`. Ports: the main gateway uses 17670; each extra gets the
  lowest free port from 17671 up (health = port+10, metrics = port+20), "free" meaning not in the
  registry and not currently bound.
- A **registry** file `<data dir>/gateways.json` lists the gateways osh created (name, kind, port,
  main, created-at). It is osh's memory of what it manages; `openshell gateway list` stays the
  source of what the CLI knows. A gateway known to the CLI but absent from the registry is
  "existing" (below).
- Where each runs:
  - **Main**: the OpenShell-provided service (Homebrew `openshell` on macOS, systemd user unit
    `openshell-gateway` on Linux) with `~/.config/openshell/gateway.toml` set to the main's kind
    and `name = "<its type name>"`.
  - **Extras**: an osh-managed service per gateway: a systemd user unit
    `osh-gateway-<name>.service` on Linux, a launchd agent `dev.guilospanck.<name>` on macOS
    (the existing label for the Docker one), both running `osh gateway-service <name>`, which
    reads `<data dir>/gateways/<name>.toml` (generated, see below) and execs
    `openshell-gateway --config` with the shared TLS dir and the gateway's own database.
- Generated config per gateway: from embedded templates per kind, filled with name, ports and
  the platform specifics (macOS Docker via Colima adds `grpc_endpoint =
  "https://host.docker.internal:<port>"`; Podman and Linux Docker rely on auto-detection unless
  the real test shows otherwise). User edits to a generated file are kept (same rule as the
  embedded data files).

## Requirements by type (what the wizard shows and installs)

| Type | macOS | Linux |
| --- | --- | --- |
| VM | `e2fsprogs` (brew) | `/dev/kvm` usable by the user (add the user to the `kvm` group when it exists but is not accessible: needs a new login, like docker), `e2fsprogs`. **Unavailable** with a reason when `/dev/kvm` does not exist |
| Docker | a Docker runtime that answers: Colima (`brew install colima docker`, `colima start`) or Docker Desktop (detected, started by the user) | Docker Engine from the distro, `docker` service enabled, user in the `docker` group, new login (existing logic) |
| Podman | `podman` (brew), `podman machine init` and `start` | `podman`, user `podman.socket` enabled (existing logic) |

Every need is a `Step` produced by the existing planner, so consent, dry-run, ordering and
resume work unchanged. Facts gain: `kvm` (absent / present but not accessible / usable),
`colima`, `docker_desktop`, `podman_machine` (none / stopped / running).

## Existing gateways

- A gateway the CLI already lists is never renamed, restarted or reconfigured by the wizard.
- `openshell` (legacy main) and `openshell-docker` (legacy extra) are recognised; their kind is
  read from the installed `gateway.toml`'s `compute_driver` (or the name). They appear in the
  Gateways tab with their kind. Reset and remove work on them as before.
- If OpenShell is already installed and a main gateway exists, everything the wizard creates is an
  extra named `openshell-<type>`, whatever order the user ticked. Only when this setup run
  installs OpenShell itself does the first ticked type become the main one, replacing the
  installer's `openshell` registration with `openshell-<type>` (add, then remove).

## Screens (layout "B"; boxes and columns measured, see the approved mockup)

1. **Machine:** what was found (OS and package manager, sudo, Docker/Podman/KVM/OpenShell
   status), each line ✓ or ✗; nothing is changed yet. `enter` continue, `q` quit.
2. **Gateways:** list on the left with `[x]` ticks and a status word (`ready`, `needs install`,
   `no KVM`); details on the right for the highlighted type (one-sentence description, a
   "What it needs" list of ✗/✓ lines such as `✗ podman  will be installed`). "1st ticked = main".
   `↑↓` move, `space` tick, `enter` continue, `?` help, `esc` back. Unavailable types cannot be
   ticked and say why. In "add" mode, types already added are shown dimmed, `already added`.
3. **Review:** one numbered plan of every step (commands as they will run, `sudo` marked), the
   gateway names and ports. `enter` Install, `b` back.
4. **Install:** live progress, one line per step (`✓` done with time, spinner, `·` pending) and
   a "Now running" box showing the current command and its latest output. A step that needs the
   user (new login, start Docker Desktop, a failed command) stays on screen with plain words and
   what to do; the wizard then ends in a state from which re-running `osh` resumes.
5. **Done:** the gateways created (name, kind, port, running), what to do next, `enter` open the
   dashboard. After a "needs a new login" stop, the screen says so instead and exits.
6. **Gateways tab:** table NAME / TYPE / PORT / STATUS (main marked), keys `enter` switch,
   `a` add, `d` reset, `x` remove, `?` help.

Style: ratatui `Block` borders, one accent colour, green/amber/red for state, dim for hints; the
layout must work at 80x24 and not break (no panics, no overlapping text) when smaller, falling
back to a stacked list without the details pane under about 70 columns.

## Behaviour details

- **Install runs the existing executor** (`setup::execute`) in a background thread, streaming
  step starts, results and output lines to the screen over a channel. Steps run with stdin closed.
  Sudo: before Install, if any step needs sudo and the ticket is not warm, the wizard leaves the
  full-screen view for one `sudo -v` prompt on the real terminal, then returns; privileged steps
  run `sudo -n`, and a step that fails because a password is required says so.
- **Order** (the existing rules, extended): curl → runtimes and their user-level needs (docker
  group + login stop, podman socket, colima, podman machine, kvm group, e2fsprogs) → OpenShell
  (only if missing) → main gateway config + service + registration → each extra gateway
  (config, service, certs copy, `gateway add`) → wait for each to answer.
- **Resume:** every step is idempotent and re-checked from facts; re-running the wizard shows
  finished types as `ready`/`added` and only plans what is missing.
- **Remove** (`x`): typed confirmation `remove`; stops and disables the gateway's service/agent,
  deletes its generated config and registration (`openshell gateway remove`), keeps its database
  unless the user types `remove and delete data`. The main gateway cannot be removed while extras
  exist; removing the last one is allowed.
- **Reset** (`d`) works for any registered gateway, using that gateway's kind for the sweep and
  its own database directory (generalising the current two hard-coded names).
- **`osh gateway-docker`** stays as an alias for adding a Docker gateway; the old macOS
  `openshell-docker` setup is the same thing under the new scheme.
- **Uninstall** also removes every osh-managed gateway service and the registry.

## Constraints

- Everything host-touching goes through `Host` and returns `Step`s; unit tests with `FakeHost`
  (the project rule). New TUI behaviour has unit tests, including rendering tests on ratatui's
  `TestBackend` that check box edges and column alignment and that nothing panics at 80x24 and 60x20.
- Keep `just check` green; keep README and the footer keys in step (the new `a`/`x` keys and the
  README tab table must agree).
- No new crates unless unavoidable (ratatui, serde_json, crossterm already present).
- Linux real tests: extend `tests/linux/real-suite.sh` for `--gateways docker,podman` (two
  gateways on real systemd, both `Connected`, names correct, main is port 17670), add, remove and
  reset of an extra, and the VM type reported `unavailable` there (no `/dev/kvm`).

## Left to the builder

Exact widths, colours and key hints within the approved look; the TOML templates (verify each with
`openshell-gateway config preflight`); the systemd unit text (derive from the packaged unit); the
registry file's exact schema; naming of internal functions. Anything the real test reveals about
Linux Docker extras needing a `grpc_endpoint` is the builder's call, recorded in the ledger.

## Calls made after the builder check (the implementer's calls, not the user's)

1. **Side by side.** Extras are separate `openshell-gateway --config` processes on their own
   ports; the packaged unit only binds 17670 (its health and metrics listeners are off by
   default), so 17671+ with health +10 and metrics +20 cannot clash. Sharing one TLS dir is
   already how the macOS Docker extra works. The real Linux test is what proves it for Linux; if
   it fails, fall back to generating a certificate set per extra (`generate-certs --output-dir`).
2. **Changing the main's `name`.** When this run installs OpenShell, the config is written before
   the first restart, so there is no extra restart. On a re-run, a main that is in the registry
   is osh's own and may be rewritten and restarted when its config drifts (the existing plan
   logic). "Never disturb existing gateways" applies to gateways not in the registry.
3. **Legacy gateways are not adopted.** `openshell` and `openshell-docker` stay as they are: not
   in the registry, listed in the Gateways tab with their kind (from `gateway.toml`'s
   `compute_driver`, or the name), reset works on them, `x` is not offered. The wizard opens
   automatically when OpenShell is missing or `openshell gateway list` is empty and the registry
   is empty; otherwise only from `osh setup` or `a`.
4. **Ports.** The main is always 17670, served by the OpenShell-provided service whatever its
   kind. Extras take the lowest port from 17671 that is not in the registry, not in any
   `openshell gateway list` endpoint and not currently bound. A legacy extra keeps its port.
5. **Selecting.** When the main is registered, osh runs `openshell gateway select <main>`.
   Adding extras does not change the selection (as today). `enter` in the tab already selects.
6. **Sudo during a long install.** The wizard runs a keep-alive (`sudo -n -v` every 50 seconds)
   while Install runs. If the ticket still expires, the step fails with "sudo needs your
   password" and the screen says to rerun.
7. **Removing.** The main cannot be removed while extras exist. Removing the only gateway stops
   and disables its service, removes the registration and registry entry, and leaves OpenShell
   itself installed (that is `osh uninstall`).
8. **macOS mixes.** VM main = Homebrew service; a Docker or Podman extra = a launchd agent. When
   the main is Docker or Podman on macOS the Homebrew service does not inherit Colima's
   `DOCKER_HOST`, so the builder chooses between giving the main its own launchd agent on 17670
   (Homebrew service stopped) and another mechanism; it must work, and since macOS cannot be run
   in the test containers the choice is covered by unit tests only and flagged as untested.
9. **Resume.** The wizard writes the chosen types to `<data dir>/wizard.json` when Install
   starts and removes it when done. A later run opens the wizard at Review with that selection
   pre-ticked, so a "log out and back in" stop resumes where it left off.
